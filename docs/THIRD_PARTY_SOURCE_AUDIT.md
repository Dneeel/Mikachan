# MIKA: third-party source audit

**Scope and method (2026-10-16).** I cloned the 21 repositories named by the owner into a temporary, read-only research area and inspected their source at the commit IDs below. References use `path:line — function`; resolve them against each section's repository and commit. “Verified” means the branch exists in source, **not** that it succeeded against a live service. I did not run these third-party bots, use their credentials, benchmark idle resource use, or modify MIKA's production VPS or Mikasa Player. README descriptions alone are not counted as implementation. No third-party code was copied into MIKA.

## Findings that matter most

1. **Catalog identity and audio provenance are separate.** Spotify and Deezer IDs can provide title, artist, album, art, duration and order. Several bots then substitute the first YouTube search result and label it with the catalog metadata. That produces plausible-looking wrong songs. MIKA must retain the selected recording's provenance, verify variant, artist and duration, and decline automatic delivery when confidence is low.
2. **Search must retain variants.** The best existing bots expose inline choices, but most search a single service. MIKA's current `src/mika_nexus/search.py:55 — Searcher.search` already accepts independent kind and source sets. It first deduplicates by `(source, kind, id)` at line 86, which preserves music versions, but then collapses podcast shows by normalized title/creator at line 111; that can merge distinct feeds. Preserve source IDs and add explicit recording/version labels.
3. **Telegram file IDs and delivery state are more valuable than another scraping dependency.** Reuse a successful upload after verifying the original source identity. Persist the file ID, media type, codec and metadata, plus an uncertain-delivery state so recovery does not resend duplicate files.
4. **Podcast RSS is a first-class source.** Apple/Spotify search helps find shows, but the public RSS feed and its enclosures are the canonical ordered episode list where available. A catalog result limited to 30 items must never be presented as a complete 221-episode show.
5. **“320 kbps MP3” often means transcoding a lower-bitrate YouTube stream.** It does not prove original quality. Preserve a verified source stream when compatible; transcode only for requested MP3/Telegram compatibility, and record the actual input/output codec and bitrate.

## Independent MIKA architecture and implementation order

1. **Contracts:** `CatalogHit(source, type, source_id, title, creators, duration, cover, version_tags, url, rights_hint)` and `MediaCandidate(actual_source, recording_id, title, creators, duration, codec, bitrate, content_length, preview_flag, url)`. Catalog fields must never overwrite the actual media identity without a match record.
2. **Discovery:** concurrent adapters for Spotify catalog (when configured), Apple Music/Podcasts, Deezer metadata, SoundCloud, YouTube Music, YouTube and RSS/Podcast Index where permitted. Enforce per-source deadline/circuit breaker and display partial results. Search source and type filters remain orthogonal. Use exact source IDs for dedupe; no normalized-title merge. Cache searches briefly and paginate server-side.
3. **Resolve and match:** for direct tracks, ask confirmation then resolve the exact catalog item; search full-length media across allowed sources using original and transliterated aliases. Apply hard vetoes for previews, wrong duration/creator or conflicting variant tokens; score positive matches. Explicitly tag `official`, `live`, `remix`, `slowed`, `remaster`, `cover`, `unofficial`, and never silently substitute. Ambiguous or unavailable cases get an honest choice/error, not a mislabeled file.
4. **Download and validate:** one bounded worker per job with retries for transient network errors, source-aware fallback, per-host budgets, byte and time limits, ephemeral workdir, ffprobe/type validation and optional deeper decode for small suspicious files. Keep source-quality audio if Telegram supports it; provide MP3 as a requested derivative. Embed only verified metadata and cover, then use `send_audio`, `send_video` and `send_photo`/album with a document option for original files.
5. **Podcasts and collections:** resolve an RSS feed when public; enumerate **all** entries in pages, preserving GUID and feed order. Direct episode links go to a confirm/download path. Bulk quality is chosen once; jobs are sent sequentially in source order with failure accounting and resume state. Do not call a feed “complete” if only a catalog page was fetched.
6. **Lyrics:** independently search licensed/permitted sources, keep source attribution and rights policy, verify title/creator/variant and reject excerpts when full text is requested. Return “unavailable” when no trustworthy permitted full text exists. A four-line excerpt must never be labeled full lyrics. Do not put full copyrighted lyrics into caches or logs without a valid basis.
7. **Operations/security:** allowlisted URL hosts and DNS/IP checks at fetch time to prevent SSRF; TLS verification on; no hardcoded tokens, shell interpolation or unreviewed decryption clients; limit redirects and files. Redact tokens and signed CDN URLs from logs. SQLite WAL stores jobs, search sessions and upload cache; idempotent Telegram delivery state, structured error reasons, source health and acceptance telemetry. Test the five owner Spotify examples plus long podcast feeds, galleries, restarts and large files against a staging bot before production claims.
