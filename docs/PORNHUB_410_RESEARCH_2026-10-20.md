# Pornhub HTTP 410 investigation · 2026-10-20

The reported `viewkey=6ac5dd5aca7cb` is not intrinsically a deleted item. From this environment, both the public watch page and `/embed/6ac5dd5aca7cb` returned HTTP 200 and included `mediaDefinitions`. The pinned yt-dlp 2026.08.19 extracted the same ID and four formats with browser impersonation. This verified extraction metadata, not a full media download or delivery to Telegram. The owner VPS could still receive HTTP 410 due to its IP, region, or the media CDN.

Upstream has reproduced the same symptom. [yt-dlp #16729](https://github.com/yt-dlp/yt-dlp/issues/16729) records HTTP 410 for browser-playable Pornhub links, with several reports that `--impersonate chrome` helped but did not work universally. [yt-dlp #17642](https://github.com/yt-dlp/yt-dlp/issues/17642) distinguishes an HTTP 410 while fetching the HLS playlist from an HTTP 410 on the watch page; one reporter could still get HTTPS formats. [#16860](https://github.com/yt-dlp/yt-dlp/issues/16860) records related HTTP 403 behavior and the need for the optional `curl_cffi` package to make impersonation available. The repository already passed `--impersonate chrome` when `curl_cffi` was installed, but its locked dependencies did not install that package. This revision locks `curl_cffi` so the existing path runs on new installations.

The next diagnostic on the affected VPS is a bounded `yt-dlp -vF --impersonate chrome` probe of the exact URL, with the user's private cookies only if the site requires them. Its sanitized stderr should identify whether the **watch page**, **HLS playlist**, or **media segment** returned 410. An embed URL with the same verified viewkey is a reasonable separate extractor probe because it exposes the same video in this environment; it is not a guaranteed bypass of a CDN or account restriction. HTTP/MP4 formats may succeed when HLS alone is rejected, but only after the exact selected format and video integrity are checked. Random proxy sites, scraped signed CDN links, and disabling TLS verification are not safe production fixes.

No server-side result is claimed: SSH to the previously supplied VPS address refused port 22 during this investigation. The bot still reports 410 if the provider rejects every supported path. The Pornhub downloader engine was not changed in this revision.
